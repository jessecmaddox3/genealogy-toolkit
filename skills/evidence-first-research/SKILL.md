# Evidence-first research

Start with one question and the user's selected local files. Read the project's README and docs/research-guide.md. Run the entirely invented demo before adapting a real workflow. Do not access unrelated records, contacts, accounts or private directories merely because they are available.

## Build a reviewable batch

1. Preserve original source text, citation, locator, access date and file hash. Distinguish an original record, a derivative, a narrative, family knowledge and a tree aggregate. Do not claim that a title or repository makes a source reliable.
2. Keep the source's claim separate from your interpretation and current conclusion. Use accepted_working, plausible_lead or quarantined_contradiction with a concrete rationale. These are working judgments, not proof scores.
3. Use stable store-wide person keys. Do not merge people by name similarity. Exact identifier links require verified identity; conflicting identifiers need resolution before import.
4. Record competing hypotheses, conflicting evidence, associates and chronology. Preserve negative searches with their actual scope. A missing entry is not proof of absence.
5. Make the next action specific: record, page or question, why it matters, and any access boundary. Do not invent citations, quotations, archive results, dates or relatives.
6. Validate the JSON, import into a disposable copy of the store, and compare the reports. A revised batch needs a new batch_id. For each explicit parent slot it mentions, include all alternatives that should remain current. Raw observations survive supersession.

## Boundaries

Use a separate private research folder. Do not publish research, upload records to a model or service, contact repositories or relatives, create accounts, place orders, make payments, or bypass access restrictions without the user's applicable authorization. Preparation is not permission to take an outside action.

Real living people belong in private seed inputs; documentary batches require deceased people. Neither condition makes reports safe to publish. Source rights/status fields are metadata, not verified licenses or completed OCR. Keep received family material and restricted sources private.

## Finish usefully

Return the current conclusion, strongest contrary evidence, remaining uncertainty and next decisive source. Link the local report files. Explain what was actually verified and what remains a lead. Use synthetic examples for code fixes, tests and public issues. General improvements belong in the reusable engine; personal configuration and records remain separate.
